# Public release verification prototype

This is a test-key prototype, not an approved release or remote-update system. Do not publish data or use production keys. Research intelligence, including MalwareBazaar data with unverified redistribution rights, stays private. A signature authenticates the manifest as authorised by a trusted key; it does not prove malware classification, upstream authenticity, or legal permission. `permitted` is a signed policy assertion and requires independent human/legal review; the prototype cannot prove that assertion or infer data origin from bytes.

The offline `public_release_signer` binary accepts a canonical manifest path and exactly 32 raw private-key bytes through standard input, and outputs the signature as hex; it is intended to run only on an approved offline host. The `public_release` Rust module signs only a versioned manifest supplied to `sign` with an external in-memory Ed25519 key. It uses `ed25519-dalek`, SHA-256, and a fixed domain separator. The only accepted encoding is the exact `serde_json` serialization of the strict typed manifest: unknown/duplicate fields, alternative ordering/whitespace/escapes, and noncanonical serializations are rejected on verification. The schema records format version, database version, release ID and number, creation/expiry Unix seconds, named artifacts with sizes and SHA-256, source provenance/classification/redistribution assertions, minimum scanner version, previous manifest hash, key identifier (SHA-256 of the public key), and algorithm. Only explicitly `permitted` redistribution claims are accepted; the known `malwarebazaar` source and `private research intelligence` classification are blocked. Renaming or misclassifying data can bypass this local label check, so independent approval remains mandatory. The code verifies every declared artifact and rejects missing or extra in-memory artifacts; release directory files not declared in the manifest are not inspected or distributed by the prototype.

`scan --public-release RELEASE_DIR --public-key TRUSTED_PUBLIC_KEY --public-state TRUSTED_STATE_DIR` invokes the prototype verifier before attaching the exact owned index. Both directories must be absolute owner-controlled 0700 directories with 0600 regular files, and the release directory must contain `manifest.json`, binary or hex `manifest.sig`, and every named artifact. Public key trust comes solely from the operator-supplied public key, not a key embedded in the release. `db init-public-state --root TRUSTED_STATE_DIR` explicitly creates initial state and fails if it already exists. It is not an updater: there is no remote fetching, signed trust-root rotation, role delegation or automatic activation. Highest accepted sequence and manifest digest are persisted atomically under a directory lock; later versions require the last accepted manifest digest, and same-sequence equivocation is rejected. If state is deleted, reset, restored from backup, or controlled by an attacker, rollback protection can be lost. Expiration depends on an honest clock. A state sync failure can leave the newly accepted state visible; investigate rather than automatically reset it.

The Update Framework separates root, targets, snapshot and timestamp metadata, supports signed key rotation, delegated trust, expiry and version checks, and is a suitable design target for a later update-management phase: https://theupdateframework.io/docs/metadata/ and https://theupdateframework.io/spec/ . The Rust TUF project describes its implementation as beta with an unstable API: https://github.com/theupdateframework/rust-tuf . Evaluate current maintained TUF client options, audit and compatibility before selecting one; this prototype is not TUF compatible and has no revocation or threshold signatures.

For future owner approval, establish an offline signing ceremony on a dedicated disconnected or hardware-backed system outside this repository, Codespaces and CI. Generate a production key there only after approval; document participants and verification of the public-key fingerprint. Back up encrypted key material or use independently controlled recovery shares in physically separate secure locations, test recovery without exposing the key, and record inventory/access. Rotate by authenticating replacement public keys through an independently trusted mechanism, publishing overlapping trust where appropriate, revoking compromised keys and reissuing metadata. This requires a reviewed trust-root/rotation mechanism; none is implemented here. Never place a production key in a checkout, Codespace, release, CI config or CTO report. Existing legacy `db keygen` and `db sign` commands are not an approved production signing ceremony. Automated tests generate ephemeral keys only in memory.
