## 1. Architectural Design & Implementation

### 1.1 Hot Reload Notification Strategy & Monitor Thread
In `crates/raxosentinel-cli/src/hot_reload.rs`, the `DatabaseManager` manages the active database lifecycle:
1. **Linux `inotify` Monitoring**: Watches the storage root directory for filesystem events (`IN_MOVED_TO | IN_CLOSE_WRITE | IN_ATTRIB | IN_CREATE | IN_DELETE`). Because pointer activation uses atomic file replacement via temporary file and rename (`rename(tmp, "current")`), watching the directory inode rather than the pointer inode guarantees that inode replacement does not break the watch.
2. **Bounded 100ms Periodic Check**: The monitor loop polls the inotify descriptor using `libc::poll` with a bounded timeout of 100ms. If inotify is unavailable or disabled by kernel policy, the monitor falls back to periodic 100ms polling.
3. **Internal Synchronization**: Reload transitions are protected by `reload_lock: Arc<Mutex<()>>`. Concurrent reload requests and monitor wakeups are serialized so multiple reloads never overlap.

### 1.2 In-Flight Scan Pinning (`PinnedDatabaseHandle`)
To guarantee that an active scan is pinned to one complete, verified RSIDB generation and never observes indicators from two generations:
1. `ActiveDatabaseHandle` encapsulates `generation: String`, `root: PathBuf`, `index: Arc<MmapSortedIndex>`, `total_indicators: usize`, `loaded_at: Instant`, `load_timings: LoadTimings`, and `active_scans: Arc<AtomicUsize>`.
2. When a scan request arrives at the coordinator in `coordinator.rs:handle_client_connection`:
   ```rust
   let pinned_handle = db_manager.map(|dm| dm.pin_active());
   ```
3. `PinnedDatabaseHandle` increments `active_scans` on creation and decrements `active_scans` on `Drop`.
4. The worker configuration passed to the supervised sandboxed worker subprocess dynamically receives `--private-generation <pinned_handle.generation()>`. The worker opens that exact generation and never touches other generations.
5. Even if an update or rollback swaps the active database in `DatabaseManager` during a long-running scan, the in-flight scan retains its `PinnedDatabaseHandle` reference. Future requests receive the new generation handle immediately.
6. When the last in-flight scan referencing the old generation drops its `PinnedDatabaseHandle`, the old generation's `Arc<MmapSortedIndex>` reference count drops to zero, and the memory mapping is immediately unmapped and reclaimed by the kernel.

### 1.3 Pre-Adoption Verification & Fail-Closed Degradation
When a new pointer target is observed:
1. Candidate directory name is checked against invalid prefixes (rejecting leading dots such as `.staging-*`).
2. Candidate staging completeness is verified via `private_store::incomplete(root)`.
3. Candidate RSIDB is opened and authenticated via `private_store::load_timed(root, target_gen)`. This verifies:
   - Header, magic bytes, endianness, index hash tables, binary layout.
   - Provenance manifest format and digest.
   - Registry and source manifest hash bindings.
   - Raw evidence verification against canonical provider records.
4. If verification fails for **any reason** (missing generation, corrupt RSIDB, mismatched metadata, malformed pointer, permission errors):
   - The candidate generation is **never** adopted.
   - The last known-good generation remains active in memory.
   - `degraded: Arc<AtomicBool>` is set to `true`.
   - `last_error: Arc<RwLock<Option<String>>>` captures the exact verification failure.
   - Incoming scan responses report `degraded_freshness: true` alongside the last known-good `database_generation`.
5. When an authorized valid release is subsequently activated, verification passes, the new generation is adopted atomically, `degraded` is cleared to `false`, and `last_error` is reset to `None`.

## 2. Pointer Race Condition & Interruption Hardening

In `crates/raxosentinel-signatures/src/rsidb/updater/status.rs` and `engine.rs`:
1. **Cyclic Pointer Elimination**: If an interruption occurred between writing `previous` and `current`, `previous` could point to the same generation as `current`. `UpdateStatus::load()` now explicitly verifies:
   ```rust
   if let Some(ref prev) = status.previous_generation {
       if status.current_generation.as_ref() == Some(prev)
           || !root.join(prev).join("database.rsidb").exists()
       {
           status.previous_generation = None;
       }
   }
   ```
2. **Rollback Guard**: `engine.rs:rollback()` now validates that `prev_gen != old_current`:
   ```rust
   if let Some(ref cur) = old_current {
       if cur == &prev_gen {
           return Err(UpdateError::RollbackFailed(format!(
               "Cyclic rollback target: previous generation equals current generation '{}'",
               prev_gen
           )));
       }
   }
   ```
3. **Atomic Pointer Writes**: `write_pointer()` continues to write to `.pointer.tmp-<pid>`, issue `sync_all()`, and atomically `rename()`. Staging generations (`.staging-*`) are never pointed to by `current`.

## 5. Summary of Compliance with Project Invariants

1. **ONE Unified Native RSIDB**: No parallel ClamAV database, no scan-time ClamAV dependency, no unverified SQLite or raw CVD evaluation during scans.
2. **Zero In-Flight Interference**: In-flight scans remain strictly pinned to their startup generation. No mixed metadata or corrupted verdicts.
3. **Fail-Closed on Tampering / Corruption**: Corrupted candidates, malformed pointers, and incomplete staging generations are unconditionally rejected. Last known-good database is retained, and degraded freshness is transparently signaled.
4. **Memory & Performance Bounded**: At most 2 generations held in memory during transitions. Switch latency measured under 30ms.
5. **Production VPS & Git Remote Boundaries**: All changes committed strictly on local branch `phase-3b`. No push to remote; no deployment to production VPS.
