2. History-aware merge
The existing merge-private operation now verifies and combines legacy single-source, v1 multi-source and v2 acquisition-history inputs into a new immutable v2 generation. It unions distinct source IDs and acquisition IDs, retains each exact evidence response, rebuilds source associations from evidence, deduplicates operational hashes and quarantines conflicting file sizes. Absence from a recent response does not withdraw prior indicators. The existing descriptor-relative staging, file sync, staged validation, directory sync, no-replace rename and containing-directory sync are retained.

New single-source acquisitions carry a random 128-bit event nonce in the local acquisition manifest. The v2 acquisition ID incorporates that nonce, source ID, timestamp and evidence digest, allowing independently published identical responses in the same second to remain distinct events. Existing manifests without a nonce and existing v2 acquisition IDs remain compatible; events that were already indistinguishable in the old format cannot be retroactively separated. Nonces and local hashes are not provider signatures. Synthetic tests merge mixed v1/v2 histories, preserve two same-second identical acquisitions, retain cross-source associations, and avoid duplicated scanner records.

5. Memory and bottlenecks
A separate 100,000-record full synthetic benchmark run measured 420,800 KiB peak process RSS using OS child-process accounting. That peak includes fixture generation, source evidence, index compilation, validation, refresh, merge, allocator retention and test harness; it is NOT incremental database memory. Incremental database memory was not reliably isolated. The measured association JSON (17,988,923 bytes) exceeded the RSIDB size (5,186,849 bytes), and the full verification/refresh path retains and reprocesses evidence. The former per-record JSON serialize-and-reparse loop was removed: the same source validation now parses each response once while retaining distinct size/family claims. No controlled before/after timing isolates that optimization. The v2 history limit was raised to a maximum of 2,048 total acquisitions, 256 MiB aggregate evidence and 64 MiB registry/association files; these remain finite safety limits, not capacity guarantees. Larger or more diverse datasets require further measured work.

6. Fault and corruption results
Synthetic tests cover partial writes, file-sync and staging-directory-sync failures, failed rename, existing destination names and a post-rename root-sync failure that reports uncertain durability. The prior valid generation remains usable. Other tests reject missing evidence, damaged registry, damaged associations, corrupted historical acquisition and invalid inputs before scanner use or merge; interrupted staging is reported and left untouched. An integration test confirms a corrupted v2 registry causes an actual scanner database-load error. These are injected failures and process-level checks, not proof of real power-loss durability or coverage of every filesystem failure.

7. Cryptographic trust, licensing and TUF review
A valid Ed25519 signature demonstrates that the holder of a trusted release-signing key signed the exact canonical manifest; it does not establish the identity or authenticity of unsigned upstream data, malware classification, or legal rights. The prototype now also requires approval.json and a raw 64-byte approval.sig signed by a DISTINCT trusted reviewer key over the exact manifest digest. The public scanner takes --public-approval-key alongside --public-key and rejects missing/forged approval, the same key in both roles, and a re-signed local metadata edit without renewed approval. Signature-only verification is internal and no longer an externally exposed public-release acceptance API. Existing known private MalwareBazaar source is still blocked. There is no claim that two keys alone establish organizational independence: an operator controlling both trust anchors can bypass intended separation, and a reviewer can make a mistaken legal assertion. No cryptographic mechanism can infer legal rights or malware truth from a hash alone.

Proposed process: maintain independently controlled evidence for each source's provider, acquisition, license or written grant, allowed derivatives, redistribution scope, reviewer, date and expiry. A reviewer separate from the release signer checks the exact source/artifact set and signs its manifest digest; any change requires renewed review. The signer signs only that approved release. Reviewer and signer keys must be bootstrapped independently and held outside Codespaces, CI and the repository. Revocation, organizational controls and approval-record governance are not implemented.

TUF separates root, targets, snapshot and timestamp roles, supports delegated trust and signed metadata expiry, and should be evaluated for future secure updates and key rotation: https://theupdateframework.io/docs/metadata/ and https://theupdateframework.io/spec/ . The rust-tuf project describes its implementation as beta and its API as unstable: https://github.com/theupdateframework/rust-tuf . This prototype is not TUF, does not implement key revocation/rotation, threshold trust, remote update, or atomic release activation. Trusted local rollback state, external trust anchors and a trustworthy clock remain required; compromise or reset limits protection. No production keys were generated.

11. Unresolved limitations
The measured 100,000-record fixture is not a production workload. Incremental DB memory and true power-loss durability were not measured. Association JSON and repeated full evidence validation remain substantial; storage, memory and refresh costs need profiling across realistic shapes and sources. Historical acquisitions lacking nonce cannot be retroactively distinguished. The only genuine source adapter remains MalwareBazaar; synthetic adapters are test-only. Independent reviewer approval is a trusted attestation, not proof of actual redistribution rights; relabelled data or compromised/replaced trust anchors require governance and independent review. The public prototype has no TUF interoperability, key rotation/revocation or secure remote update and must not be distributed as production-ready.
