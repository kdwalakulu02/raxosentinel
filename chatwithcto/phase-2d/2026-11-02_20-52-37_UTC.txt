Source inspection, refresh and comparison
The existing db sources and db indicator commands validate evidence first and support legacy, v1 multi-source and v2 acquisition-history generations. JSON source views include provider, acquisition IDs, timestamps, evidence hashes and counts. Indicator views include source-specific claims, family labels and a conflicting-file-size quarantine reason. db compare-private reports added, retained, removed and quarantined hashes, source changes and acquisition ID changes. Output contains private intelligence and must remain private.

  raxosentinel db sources --root PRIVATE_ROOT --generation GENERATION
  raxosentinel db indicator --root PRIVATE_ROOT --generation GENERATION SHA256_HEX
  raxosentinel db refresh-private-source --root PRIVATE_ROOT --input OLD --replacement NEW_ACQUISITION --output REFRESHED --source malwarebazaar
  raxosentinel db compare-private --root PRIVATE_ROOT --before OLD --after REFRESHED

Refresh creates an immutable v2 generation, preserving exact older and newer response bytes in separate private evidence files. Acquisition IDs bind source ID, recorded timestamp and evidence SHA-256; the registry tracks counts of new and previously known indicators, duplicate observations and conflicting sizes. Existing scanner records are reconstructed from all verified evidence and deduplicated. Conflicting size claims, including distinct sizes in the same response, quarantine the hash. Removing a source rebuilds another generation; another source's overlapping indicators remain. Tests show A/B/C plus B/C/D yields A/B/C/D, two retained acquisitions, one newly observed and two previously known in the second acquisition, and corruption of historical evidence is rejected. Inputs remain unchanged. Timestamps are locally recorded metadata, not provider signatures.

Cryptographic architecture and signed-manifest format
The prototype uses Ed25519 from the existing ed25519-dalek Rust dependency and SHA-256. A fixed domain-separated signature covers one exact canonical typed JSON serialization: strict typed fields, denial of unknown fields and byte-for-byte reserialization reject alternative whitespace, key order, escaping and duplicate-field interpretations. The version-1 manifest includes database version, release ID and monotonically increasing number, creation/expiry Unix seconds, named artifact digests and byte sizes, source IDs and provenance/classification/redistribution assertions, minimum scanner version, optional previous manifest SHA-256, key ID derived from the trusted public key, and algorithm ID. All declared files must be present and hash/size correct; the database must pass RSIDB validation. The prototype does not enumerate undeclared files in a release directory and does not establish the semantic truth of a signed registry or association table from upstream evidence.

Only explicit permitted redistribution claims are accepted. The known malwarebazaar source ID and private research intelligence classification are blocked. An operator who relabels or misclassifies data can evade label-based policy: an independently reviewed source-permission and origin approval process is required. A signature proves authorisation by a trusted signing key, not malware classification, upstream source authenticity or legal redistribution rights. Existing private research data must not be publicly released.

Verification enforcement point and rollback state
The new explicit scanner mode --public-release RELEASE_DIR --public-key TRUSTED_PUBLIC_KEY --public-state TRUSTED_STATE_DIR loads an owned database only after verifying the canonical manifest, trusted Ed25519 key, signature, expiry, scanner version, all named artifact sizes and hashes and RSIDB structure. A failure returns a database-load error rather than a clean scan or unsigned fallback. The legacy --db and --db-store options remain explicitly unverified legacy workflows; they are not the public-release prototype. The private research --private-db-root workflow stays separate.

A 0700 owner-controlled state root is explicitly initialized with db init-public-state --root TRUSTED_STATE_DIR; automatic reset is not performed. The public loader serializes access with a lock and persists the highest accepted release number and manifest digest, checks the previous digest on advancement, rejects older numbers and same-number equivocation, and syncs the state file and directory. This provides only local prototype rollback protection: deleting, resetting, restoring or compromising local state can remove the guarantee, and an incorrect/compromised system clock undermines expiry. No secure remote update, independent root-of-trust policy, atomic release activation, key revocation, threshold signatures, recovery protocol or signed rotation is implemented. The explicitly supplied public key is the trust anchor; trust bootstrap and replacement require an external trusted procedure.

Signing-key management
The standalone public_release_signer accepts a canonical manifest path and exactly 32 raw key bytes from standard input, emits a signature, and does not write the key. It is intended only for an approved separate offline signing environment. Tests generated ephemeral keys in memory; no production key was generated, stored or committed. The existing legacy db keygen/sign commands are not an approved production ceremony. Future owner-approved procedures must cover isolated/offline or hardware-backed key generation outside the repository, Codespaces and CI, independent fingerprint verification, encrypted geographically separate backups or controlled recovery shares, tested recovery, and audited rotation/revocation. The prototype has no implemented trusted root-rotation or key revocation mechanism; memory-copy erasure and hardware isolation are not guaranteed by this prototype.

TUF assessment
The Update Framework's root, targets, snapshot and timestamp metadata and delegated trust offer an established model for separate trust roles, expiration, rollback/freeze resistance and key rotation: https://theupdateframework.io/docs/metadata/ and https://theupdateframework.io/spec/ . The Rust TUF implementation describes itself as beta with an unstable API: https://github.com/theupdateframework/rust-tuf . Evaluate a current maintained TUF implementation, audit and operational compatibility in a dedicated secure-update phase. This signed-manifest prototype is not TUF-compatible and does not implement a remote update protocol.

Outstanding limitations and next CTO decision
The previous v1 multi-source merge command does not accept v2 history inputs; v2 supports verified inspection, additive refresh and source removal. Acquisition IDs use source, second-resolution timestamp and evidence digest, so independently repeated identical responses for the same source in the same second cannot be distinguished and collapse as the same acquisition. No repeatable storage or performance benchmark was made for v2. Multi-file publication and state handling have no real power-loss proof. The prototype does not verify that the manifest's permitted-source assertions correspond to real-world legal rights or that signed metadata truthfully describes all indicators. Legacy unsigned workflows remain available when explicitly selected. Do not deploy or publish on the strength of this prototype. The CTO must decide whether to commission a separate TUF-based secure-update, independent redistribution-policy and key-governance phase, and whether broader crash testing and history-aware merge support are required.
