## 2. What Was Implemented

### Single Canonical Runtime Architecture (ONE RSIDB)
- In strict adherence to RaxoSentinel architectural directives, **there is only ONE canonical runtime intelligence database: RSIDB (`database.rsidb`)**.
- No separate ClamAV database, parallel scanning engine, or compatibility emulation layer was introduced. ClamAV and MalwareBazaar act exclusively as input intelligence sources.
- Indicators from all sources are converted directly into RaxoSentinel's native binary format (`SignatureEntry`), sorted monotonically, indexed with a 2-byte compact prefix directory, and compiled with cryptographic provenance manifests.

### Multi-Source Ingestion & Evidence Attribution Pipeline
- **Unified Registry & Associations (`raxosentinel-unified-v1`):**
  - Designed and implemented `UnifiedSource`, `UnifiedRegistry`, `UnifiedAssociations`, `UnifiedIndicator`, and `UnifiedClaim` in `crates/raxosentinel-signatures/src/rsidb/malwarebazaar/private_store/unified.rs`.
  - Supports tracking source ID, provider, acquisition method, timestamp, classification, provenance, redistribution license, and cryptographic evidence hashes.
  - Implemented `publish_unified()`, enforcing atomic generation creation and immutable directory protections (0700 dir, 0600 files).
- **ClamAV Whole-File Hash Acquisition & Ingestion Pipeline:**
  - Implemented `crates/raxosentinel-cli/src/bin/populate_unified_rsidb.rs`.
  - Loaded official ClamAV exclusion databases:
    - 996 false-positive exclusion hashes loaded from `.fp` and `.sfp` files (`main.fp`, `main.sfp`, `daily.fp`, `daily.sfp`).
    - 24 ignored/revoked signature names loaded from `.ign` and `.ign2` files (`daily.ign`, `daily.ign2`).
  - Filtered and ingested whole-file hash signatures from `.hdb` and `.hsb` files (`main.hdb`, `main.hsb`, `daily.hdb`, `daily.hsb`).
  - Enforced strict hash format rules:
    - MD5 (16 bytes, 32 hex chars)
    - SHA-1 (20 bytes, 40 hex chars)
    - SHA-256 (32 bytes, 64 hex chars)
    - Preserved exact algorithm semantics: **never invented SHA-256 equivalents for MD5 or SHA-1**.
    - Rejected wildcard file sizes (`*`), preserving strict file size validation.
    - Filtered false-positive and ignored entries.
- **MalwareBazaar Ingestion & Preservation:**
  - Preserved all 104 genuine operational SHA-256 indicators from `phase2d4-refreshed-final`.
  - Maintained complete acquisition evidence files (`acq-130bdc21...` and `acq-7009a4d2...`) and sidecar digests.

## 5. Unsupported ClamAV Signature Types & Analysis

During inspection of official ClamAV CVD distributions (`main.cvd` and `daily.cvd`), 3,099,065 signatures were identified that cannot be represented as whole-file cryptographic hashes:

1. **PE Section Hashes (`.mdb`, `.msb`): 2,670,550 signatures**
   - *Technical Reason for Rejection:* These signatures match hashes of individual executable sections (e.g. `.text`, `.data`) rather than the entire file. Attempting to match them against whole-file digests would result in false negatives.
   - *Engineering Path Forward:* Requires integrating a safe, zero-unsafe, bounded PE32/PE32+ header parser within the supervised worker. The parser must validate DOS/NT headers, SectionHeaders, and virtual offsets with strict bounds checks before extracting section slices for hashing.
2. **Byte Pattern Signatures (`.ndb`, `.ndu`): 106,069 signatures**
   - *Technical Reason for Rejection:* These contain variable-length sub-sequence patterns with wildcards (`??`), byte ranges (`(aa|bb)`), regex jumps (`{-n}`), and offset anchors. They are not fixed cryptographic hashes.
   - *Engineering Path Forward:* Expand RaxoSentinel's existing Aho-Corasick automaton to support bounded wildcard patterns and anchored offsets without degrading streaming performance.
3. **Logical Signatures (`.ldb`, `.ldu`): 322,446 signatures**
   - *Technical Reason for Rejection:* These combine multiple byte patterns, container metadata, and file type criteria using Boolean logic expressions (`A & B & !C`).
   - *Engineering Path Forward:* Requires a strictly bounded AST evaluator with recursion depth limits and execution time budgets to avoid Denial of Service on hostile inputs.
