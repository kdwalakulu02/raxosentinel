Overall Audit Verdict: VERIFIED WITH LIMITATIONS

Plain-Language Explanation:
The RaxoSentinel repository on branch `phase-3b` at commit `1e77ba04a2dbfb4cc9b83ba376ba05d487d7146d`
is a genuine, compiling, well-structured Rust prototype that passes all 129 active
unit and integration tests plus its release-mode concurrency benchmark suite with zero
compiler or Clippy warnings. Core security invariants claimed across Phases 2D.3–3B.3
are substantively implemented in source code:
  1. The persistent coordinator (`raxosentinel serve`) and supervised worker actually
     invoke `private_store::load`, which enforces mandatory cryptographic evidence
     verification across all three private database formats (`sidecar-v1`,
     `multisource-v1`, and `multisource-history-v2`), independently re-derives source
     associations, excludes size-conflicting quarantined indicators, and fails closed
     on tampering.
  2. The supervised worker applies `PR_SET_NO_NEW_PRIVS`, `close_range(3, u32::MAX, 0)`,
     and a zero-access Landlock ABI 1 filesystem ruleset (`crates/raxosentinel-cli/src/main.rs:501-506`)
     strictly BEFORE reading any untrusted target bytes from the sealed `memfd` snapshot
     (`scan_descriptor` at `main.rs:518`).
  3. The signed-public release loader (`public_release::local::load`) enforces Ed25519
     release and independent reviewer signatures, key separation (`reviewer != release_key`),
     and serializes rollback-state inspection and atomic update under an exclusive
     `flock(LOCK_EX)` lock.

However, the audit uncovered significant discrepancies between previous handover reports
and the actual code, as well as concrete architectural and security limitations that
block production deployment:
  - Inaccurate Phase 3B.3 Handover Reporting: The previous Phase 3B.3 report falsely
    stated that private generations use `rules.rsidb` and `metadata.json` and that
    workers memory-map `MmapCompactDirIndex`. In reality, private generations use
    `database.rsidb` (plus format-specific evidence/registry/association files) and
    load into a heap-allocated `Vec<u8>` via `MmapSortedIndex` (which does not use `mmap`).
  - Per-Scan Full Database Re-Verification Bottleneck: The coordinator verifies the
    database at startup and discards it; every spawned worker process reloads and
    re-verifies the entire database and all raw evidence files from disk before scanning.
    For `--public-release`, every worker also acquires an exclusive `flock(LOCK_EX)`
    during load, serializing concurrent worker startups.
  - Slow-Client ("Slowloris") Worker Starvation: `recv_fd_request` relies on `SO_RCVTIMEO`
    (`stream.set_read_timeout`), which only bounds individual `read()`/`recvmsg()` calls
    rather than enforcing a total request read deadline. A local client dripping 1 byte
    every `(client_timeout_secs - 1)` seconds can tie up a coordinator worker thread for
    up to `65,536 * (client_timeout_secs - 1)` seconds.
  - Snapshot Memory Budget Bypass on Concurrent File Growth: `SnapshotReservation::update`
    adjusts `in_flight_snapshot_bytes` after `sealed_snapshot` finishes without re-checking
    `max_total_snapshot_bytes`, allowing files that grow between `fstat` and snapshot copy
    to push total in-flight snapshot memory past the configured coordinator cap.
  - Substring-Based Multipart MIME Boundary Check: `validate_mime_boundaries` checks
    for `--<boundary>--` via unanchored substring search across `raw_bytes`, allowing a
    truncated multipart email to pass boundary validation if the closing delimiter string
    appeared earlier inside a benign part body.
  - Test-Only Multi-Source Adapters: Non-MalwareBazaar multi-source adapters
    (`test_source_a`, `test_source_b`) are gated behind `#[cfg(test)]` inside the
    `raxosentinel-signatures` library crate, so the compiled CLI binary and coordinator
    integration tests only exercise single-source `malwarebazaar` generations.

[HIGH-01] Per-Read Socket Timeout (`SO_RCVTIMEO`) Allows Slow-Client ("Slowloris")
          Starvation of Coordinator Worker Threads
--------------------------------------------------------------------------------
- Severity          : HIGH
- Location          : `crates/raxosentinel-cli/src/coordinator.rs:458-593, 765, 1003-1028`
- Why It Is a Problem:
  When the coordinator's accept loop admits a connection, it pushes the raw
  `UnixStream` into `pending_queue` (`coordinator.rs:1100`). A worker thread pops
  the stream, increments `active_workers`, calls
  `stream.set_read_timeout(Some(Duration::from_secs(client_timeout_secs)))`
  (`coordinator.rs:765`), and invokes `recv_fd_request(&mut stream)`.
  `set_read_timeout` configures Linux `SO_RCVTIMEO`, which only bounds the
  inactivity duration of a single `recvmsg()` or `read()` syscall. Inside
  `recv_fd_request`, the payload loop (`coordinator.rs:568-582`) repeatedly calls
  `stream.read(&mut chunk)` until `payload_len` (up to `MAX_REQUEST_PAYLOAD = 65,536`
  bytes) is received, without checking total elapsed wall-clock time.
- Reproducible Failure Scenario:
  An authorized local client (or compromised process running under `--authorized-uid`)
  opens `max_workers + max_pending` connections to the Unix socket, sends a valid
  1-FD `SCM_RIGHTS` header declaring `payload_len = 65536`, and then writes 1 byte
  every 4 seconds (with default `--client-timeout-secs = 5`). Neither `SO_RCVTIMEO`
  nor `worker_timeout_ms` ever triggers. All `max_workers` threads remain blocked
  in `recv_fd_request` for up to `65,536 * 4s = 262,144s` (~72.8 hours), causing a
  complete denial of service (all subsequent legitimate requests receive `BUSY`).
- Recommended Fix   :
  Pass an `Instant` deadline (`Instant::now() + Duration::from_secs(client_timeout_secs)`)
  into `recv_fd_request`. Before each `recvmsg`/`read` iteration, compute
  `remaining = deadline.checked_duration_since(Instant::now())`, return a timeout
  error immediately if `remaining` is `None` or zero, and set `stream.set_read_timeout(Some(remaining))`.
- Blocks Production : YES

[HIGH-02] Per-Scan Full Database and Evidence Re-Verification in Every Spawned
          Worker Causes Severe CPU/I/O Amplification and Lock Contention
--------------------------------------------------------------------------------
- Severity          : HIGH
- Location          : `crates/raxosentinel-cli/src/coordinator.rs:194-251, 906`
                      `crates/raxosentinel-cli/src/supervised.rs:209-257`
                      `crates/raxosentinel-cli/src/main.rs:414-466`
                      `crates/raxosentinel-signatures/src/rsidb/public_release.rs:531-654`
- Why It Is a Problem:
  1. `raxosentinel serve` verifies the configured private generation or signed-public
     release at startup (`verify_startup_database`, `coordinator.rs:194-251`) and
     immediately drops the resulting `MmapSortedIndex`.
  2. For every scan request, `execute_worker_on_snapshot` spawns a fresh
     `raxosentinel scan --worker-internal` process that re-reads `database.rsidb`
     into a heap `Vec<u8>`, re-reads and SHA-256 hashes every evidence/artifact file,
     re-parses all raw JSON records, re-derives all associations, and verifies every
     entry against the index before applying Landlock.
  3. While the Phase 3B.3 benchmark used a 1-record synthetic database (~5 ms startup),
     Phase 2D.4 measurements (`chatwithcto/phase-2d/2026-11-02_21-10-45_UTC.txt:25`)
     show that verifying a 100,000-record `multisource-history-v2` generation takes
     ~2.76 seconds and ~197 MiB RSS per load. Spawning 4 concurrent workers on a
     100k-record generation would consume ~11 CPU-seconds and ~800 MiB of transient
     verification memory per 4 scans.
  4. In `--public-release` mode, `public_release::local::load` acquires an exclusive
     `flock(LOCK_EX)` on `public-release-lock` (`public_release.rs:534`) and holds it
     while reading and verifying up to 128 MiB of artifacts (`public_release.rs:551-598`),
     serializing concurrent worker startups on a single file lock.
- Reproducible Failure Scenario:
  Start `raxosentinel serve --max-workers 4` with a 50,000-record `multisource-history-v2`
  generation and submit 4 concurrent 1 KB files with `--worker-timeout-ms 1000`. All 4
  workers spend >1,000 ms re-verifying raw acquisition JSON files before `scan_descriptor`
  is even reached, causing every scan to fail with a worker timeout (`ERROR`).
- Recommended Fix   :
  Verify and compile the `SignatureDatabase` + `MmapSortedIndex` once in the
  coordinator at startup, serialize the validated index into a read-only sealed
  `memfd` (`F_SEAL_WRITE | F_SEAL_SHRINK | F_SEAL_GROW | F_SEAL_SEAL`), and pass that
  sealed FD to each worker (or fork workers from a pre-initialized template / pass
  the verified sealed `database.rsidb` FD), allowing the worker to enter Landlock
  immediately without touching the filesystem or acquiring `public-release-lock`.
- Blocks Production : YES

[MEDIUM-01] Global Snapshot Memory Accounting Can Exceed `max_total_snapshot_bytes`
            When Target File Grows Between `fstat` and `sealed_snapshot`
--------------------------------------------------------------------------------
- Severity          : MEDIUM
- Location          : `crates/raxosentinel-cli/src/coordinator.rs:696-708, 783-886`
- Why It Is a Problem:
  In `handle_client_connection`, the coordinator calls `fstat(raw_fd)` (`line 783`)
  to obtain `file_size`, reserves `file_size` bytes via `SnapshotReservation::new`
  (`line 837`), and then copies up to `max_size` bytes from `raw_fd` into a `memfd`
  via `sealed_snapshot(source, max_size)` (`line 869`). Afterward (`line 884-886`),
  it calls `reservation.update(meta.len())`.
  Inside `SnapshotReservation::update` (`lines 699-701`), if `actual_bytes > self.reserved_bytes`,
  it executes:
  `guard.in_flight_snapshot_bytes = guard.in_flight_snapshot_bytes.saturating_add(diff);`
  without checking whether `guard.in_flight_snapshot_bytes + diff > guard.max_total_snapshot_bytes`!
  Furthermore, the `memfd` bytes have already been allocated in kernel tmpfs during
  `sealed_snapshot` before `reservation.update` is called.
- Reproducible Failure Scenario:
  Configure `--max-workers 4 --max-total-snapshot-bytes 52428800` (50 MiB) and
  `--max-size 52428800` (50 MiB). A client opens 4 empty (0-byte) files, submits all
  4 FDs concurrently (`fstat` sees `file_size = 0`, so all 4 pass `SnapshotReservation::new`
  with 0 bytes reserved), and concurrently appends 50 MiB to each file while
  `sealed_snapshot` is reading. `sealed_snapshot` caps each file at `max_size` (50 MiB),
  allocating `4 * 50 MiB = 200 MiB` of in-flight `memfd` snapshots—4x the configured
  `max_total_snapshot_bytes` budget.
- Recommended Fix   :
  Cap `sealed_snapshot` for a given request at `min(max_size, remaining_snapshot_budget)`,
  or reserve chunks incrementally through `SnapshotReservation` inside the
  `sealed_snapshot` read loop so any growth past `max_total_snapshot_bytes` aborts
  snapshot creation immediately before allocating additional `memfd` pages.
- Blocks Production : YES

[MEDIUM-02] Unanchored Substring Search in `validate_mime_boundaries` Can Miss
            Truncated Multipart MIME Containers
--------------------------------------------------------------------------------
- Severity          : MEDIUM
- Location          : `crates/raxosentinel-email/src/scanner.rs:876-935`
- Why It Is a Problem:
  `validate_mime_boundaries` verifies that a `multipart/*` message contains its
  opening (`--<boundary>`) and closing (`--<boundary>--`) delimiters by calling
  `bytes_contains(raw_bytes, close_delim.as_bytes())` (`scanner.rs:907, 923`).
  `bytes_contains` (`scanner.rs:876-881`) performs a raw sliding-window substring
  search across the entire `raw_bytes` slice without requiring `--<boundary>--` to
  appear on its own MIME boundary line or after the last parsed MIME part.
- Reproducible Failure Scenario:
  Construct a `multipart/mixed; boundary="BOUND"` email where Part 1 (`text/plain`)
  contains the benign text `"Note: do not use --BOUND-- in this text"`, followed by
  `--BOUND\r\nContent-Type: application/octet-stream\r\n\r\n` and a truncated
  payload with no closing `--BOUND--` at the end of the file. `mail_parser` parses
  the available bytes, and `validate_mime_boundaries` returns `Ok(())` because
  `--BOUND--` appeared as a substring inside Part 1. If neither Part 1 nor the
  truncated bytes of Part 2 match a signature, the email is reported as `CLEAN`
  instead of `UNSCANNED` (`ScanStatus::Unsupported`).
- Recommended Fix   :
  Verify that `--<boundary>--` occurs at a valid RFC 2046 line boundary (`^--<boundary>--[ \t]*(\r?\n|$)`)
  located at or after the end offset (`part.offset_end()`) of all child parts
  belonging to that multipart container.
- Blocks Production : YES

  Running `raxosentinel scan --private-db-root <root> --private-generation <gen>` on a
  multi-source generation containing `"test_source_a"` fails with
  `Error: private database rejected: Unsupported private source adapter`.
- Recommended Fix   :
  Implement the production source adapters (or a generic schema-validated private
  evidence adapter) in non-test builds and add an integration test in
  `crates/raxosentinel-cli/tests/coordinator.rs` exercising `raxosentinel serve` against
  both `raxosentinel-multisource-v1` and `raxosentinel-multisource-history-v2` generations.
- Blocks Production : NO (Blocks multi-feed private deployments beyond MalwareBazaar)

[LOW-01] Public Verification Key and External Rule Pack Loaders Do Not Enforce
         Owner-Only Permissions or `O_NOFOLLOW`
--------------------------------------------------------------------------------
- Severity          : LOW
- Location          : `crates/raxosentinel-signatures/src/rsidb/crypto.rs:79-85`
                      `crates/raxosentinel-signatures/src/loader.rs:26-31`
                      `crates/raxosentinel-cli/src/main.rs:416, 437-440`
                      `crates/raxosentinel-cli/src/coordinator.rs:236-238`
- Why It Is a Problem:
  While `private_store::root`/`readat` and `public_release::local::load` strictly
  enforce `O_NOFOLLOW`, `st_uid == geteuid()`, `st_nlink == 1`, `0700` directory mode,
  and `0600` file mode on `--private-db-root`, `--public-release`, and `--public-state`,
  the loaders for `--public-key`, `--public-approval-key` (`crypto::load_verifying_key_from_file`),
  and `--rules` (`load_rules_from_file`) use `std::fs::read(path)` directly without
  checking symlink status, file owner UID, or group/world write permissions.
- Reproducible Failure Scenario:
  If an operator places `public.key`, `approval.key`, or `rules.json` in a shared
  directory (e.g., `/tmp` or a group-writable config directory) or with `0666` mode,
  another local user can replace the key or rule file via symlink or overwrite without
  RaxoSentinel rejecting the insecure file permissions.
- Recommended Fix   :
  Open `--public-key`, `--public-approval-key`, and `--rules` with
  `O_NOFOLLOW | O_NONBLOCK | O_CLOEXEC` and verify via `fstat` that `st_uid == geteuid()`
  (or root `0`), `S_IFREG`, and `(st_mode & 0o022) == 0`.
- Blocks Production : NO (Defense-in-depth hardening)

[LOW-02] Socket Preparation and Cleanup Have Minor Path-Based TOCTOU Windows
--------------------------------------------------------------------------------
- Severity          : LOW
- Location          : `crates/raxosentinel-cli/src/coordinator.rs:254-368`
- Why It Is a Problem:
  In `prepare_socket`, the parent directory is validated to be owned by `geteuid()`
  with mode `0700` (`lines 266-305`), which prevents other non-root UIDs from racing
  inside the directory. However:
  1. `UnixListener::bind(socket_path)` creates the socket with the process's current
     `umask` before `std::fs::set_permissions(socket_path, 0o600)` is called (`lines 348-353`).
  2. `cleanup_socket` (`lines 359-368`) checks `symlink_metadata(socket_path)` and
     removes `socket_path` by path without verifying the inode number (`st_ino`/`st_dev`)
     bound by this coordinator instance.
  3. As documented in `SUPERVISED.md:13-17`, ancestor directories above `socket_path.parent()`
     are not checked for symlinks or world-writable permissions.
- Reproducible Failure Scenario:
  Same-UID processes can race `prepare_socket`/`cleanup_socket` (though same-UID
  isolation is explicitly disclaimed). If `umask` is `0000` and parent directory
  traversal is somehow bypassed before `chmod 0700` completes, the socket file is
  briefly world-writable between `bind` and `set_permissions` (mitigated by
  `SO_PEERCRED` check on accept).
- Recommended Fix   :
  Record `(st_dev, st_ino)` of the bound socket after `UnixListener::bind` and verify
  they match in `cleanup_socket` before unlinking.
- Blocks Production : NO

--------------------------------------------------------------------------------
[LOW-03] Absence of cgroup v2 Memory/PIDs Enforcement and Seccomp Syscall Filter
         in Supervised Worker
--------------------------------------------------------------------------------
- Severity          : LOW (Correctly Disclaimed in `SUPERVISED.md` and Phase 3B.3 Report)
- Location          : `crates/raxosentinel-cli/src/supervised.rs:35-79, 271-297`
                      `crates/raxosentinel-cli/SUPERVISED.md:28-44`
- Why It Is a Problem:
  The supervised worker uses `RLIMIT_AS`, `PR_SET_NO_NEW_PRIVS`, `close_range`,
  Landlock ABI 1, and process-group `SIGKILL`. Because `EmailScanner` and
  `MmapSortedIndex` are 100% safe Rust (no C/C++ parsing libraries), memory-corruption
  RCE risk during parsing is low. However, if arbitrary code execution inside the
  worker were ever achieved:
  1. Landlock ABI 1 restricts filesystem access only; it does not block `fork`/`clone`,
     `setsid`/`setpgid` (which would allow a compromised child to escape the negative-PID
     process group `SIGKILL` in `terminate_group`), or abstract Unix sockets/network.
  2. `RLIMIT_AS` caps per-process virtual address space, not physical RSS across a
     forked process tree.
  Both limitations are honestly and explicitly documented in `SUPERVISED.md:28-44`.
- Recommended Fix   :
  Before production deployment, run the coordinator under a dedicated unprivileged
  service UID/GID with a systemd unit / cgroup v2 slice (`MemoryMax=`, `TasksMax=`,
  `PrivateNetwork=yes`) and add a strict seccomp-bpf allowlist after Landlock lockdown.
- Blocks Production : YES (for untrusted production MTA deployment; acceptable for Phase 3B prototype)

E. CTO RECOMMENDATION
================================================================================

1. Does Phase 3B.3 Deserve Acceptance?
   YES, WITH CONDITIONS (Accept as a Research Prototype Milestone; Do Not Deploy to
   Production).
   The Phase 3B.3 code meets its core prototype objectives: bounded worker pool
   (1, 2, 4 workers), bounded pending queue, immediate `BUSY` overload response,
   `SO_PEERCRED` authentication, `SCM_RIGHTS` descriptor passing, sealed `memfd`
   snapshots, Landlock worker isolation before untrusted input parsing, and `flock`-
   serialized signed-public rollback state. However, the inaccurate database file
   descriptions in the Phase 3B.3 handover report (`rules.rsidb`/`metadata.json`)
   must be corrected in project documentation, and the security findings in Section C
   must be resolved before any MTA/Raxo Email integration.

2. Which Earlier Phases Remain Trustworthy?
   - Phase 2D.3 (Multi-Source Signature Database) & Phase 2D.4–2D.5 (History-Aware
     Database & Signed-Release Prototype): TRUSTWORTHY in library logic
     (`raxosentinel-signatures`), with the caveat that non-MalwareBazaar source
     adapters (`test_source_a`/`b`) are currently `#[cfg(test)]`-only.
   - Phase 3A (File, ZIP & MIME Scanning): TRUSTWORTHY for exact-hash, byte-pattern,
     ZIP, and Base64/QP inspection, subject to fixing the unanchored substring check
     in `validate_mime_boundaries` (`[MEDIUM-02]`).
   - Phase 3B.1 & 3B.1H (Supervised Worker & Hardening): TRUSTWORTHY as a Linux
     process-isolation layer; execution order (`restrict_worker_filesystem` before
     `scan_descriptor`) is verified.
   - Phase 3B.2 & 3B.3 (Persistent Local Coordinator & Bounded Concurrency):
     TRUSTWORTHY for cooperative local clients and small signature databases; requires
     remediation of `[HIGH-01]`, `[HIGH-02]`, and `[MEDIUM-01]` before handling
     adversarial local clients or large (10k–100k record) signature generations.

3. Which Issues Require Immediate Repair?
   - `[HIGH-01]`: Replace per-read `SO_RCVTIMEO` timeout in `recv_fd_request` with an
     enforced total wall-clock request deadline so slow-loris clients cannot starve
     worker threads.
   - `[HIGH-02]`: Eliminate per-scan full database and evidence re-verification in
     worker processes by loading/verifying the database once in the coordinator and
     passing a sealed read-only `memfd` index to workers.
   - `[MEDIUM-01]`: Enforce `max_total_snapshot_bytes` during `sealed_snapshot` copy
     (not merely on initial `fstat` size) so concurrently growing files cannot exceed
     the coordinator's snapshot memory budget.
   - `[MEDIUM-02]`: Anchor `--<boundary>--` validation in `validate_mime_boundaries`
     to RFC 2046 line boundaries at the end of the multipart structure.

4. Is Proceeding to Phase 3B.4 Justified?
   NOT UNTIL `[HIGH-01]`, `[HIGH-02]`, `[MEDIUM-01]`, and `[MEDIUM-02]` ARE FIXED.
   A targeted hardening pass (Phase 3B.3H) should resolve these four issues and add
   multi-source (`v1`/`v2`) coordinator integration tests before advancing to
   Phase 3B.4 (e.g., zero-reload shared index / hot database reload / MTA integration).

5. Next Three Highest-Priority Engineering Tasks:
   - Priority 1 (Coordinator Shared Sealed Database Index — Fixes `[HIGH-02]` & `[MEDIUM-04]`):
     Have `raxosentinel serve` verify the private generation or signed-public release
     once at startup, place the validated RSIDB binary into a write-sealed `memfd`
     (and support real `mmap` over that sealed FD), pass the sealed FD to each worker
     so workers enter Landlock immediately with zero disk I/O or lock contention, and
     enable multi-source (`v1`/`v2`) integration tests in `tests/coordinator.rs`.
   - Priority 2 (Total Request Read Deadline & Incremental Snapshot Accounting — Fixes `[HIGH-01]` & `[MEDIUM-01]`):
     Enforce a strict wall-clock deadline across the entire `recv_fd_request` framing
     loop, and enforce `max_total_snapshot_bytes` incrementally inside `sealed_snapshot`

     Harden `validate_mime_boundaries` in `crates/raxosentinel-email/src/scanner.rs`
