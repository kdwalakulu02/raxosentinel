1. ARCHITECTURE & COORDINATOR SERVICE
- Daemon: Implemented `raxosentinel serve` command listening strictly on a Unix domain socket. No TCP listener or network exposure exists.
- Socket Directory & Permissions: Safe directory validation enforces owner-controlled restrictive permissions (0700). Parent directories must be owned by the current process UID; attempts to use insecure or foreign directories are refused. The socket file is created with 0600 permissions.
- Stale Socket & Safe Cleanup: Symlink metadata inspection verifies socket ownership and file type before binding or unlinking. Symlinks, regular files, and foreign sockets are never overwritten or removed. Stale sockets from crashed instances are safely verified via connection failure and cleaned up on startup. Clean exit (SIGINT/SIGTERM) unlinks only the verified socket file.
- Client Authentication: OS peer credentials (`SO_PEERCRED`) verify the connecting client's UID against the configured authorized UID (`--authorized-uid`, default current process UID). Unauthorized clients are rejected immediately with an explicit ERROR status without executing scans.
- Concurrency & Queue Scope: Enforces one active scan at a time via a dedicated worker runner thread and a bounded synchronization channel (`sync_channel`, default `--max-pending 1`). Connections beyond admitted capacity receive an immediate, non-blocking structured `BUSY` verdict with write shutdown and incoming drain to prevent connection reset races. No unbounded queue, threads, or memory accumulation can occur.
- Resilience: The coordinator survives individual scan failures, client disconnects, worker crashes, and worker timeouts, continuing to serve subsequent requests cleanly.

2. CLIENT INTERFACE & FILE DESCRIPTOR PASSING
- Client: Implemented `raxosentinel client --socket <PATH> <TARGET>` and preserved `raxosentinel scan --socket <PATH> <TARGET>`.
- Descriptor Passing: The client opens the target file locally with `O_NOFOLLOW | O_CLOEXEC` and transfers the open descriptor to the coordinator via `SCM_RIGHTS`. The coordinator never opens arbitrary file paths supplied by clients.
- Descriptor Validation: The coordinator inspects the received descriptor using `fstat`. Exactly one descriptor must be received; missing descriptors, extra descriptors (including `MSG_CTRUNC` truncation), directory descriptors, pipe/FIFO descriptors, and non-regular files are rejected with structured ERROR responses. Received descriptors are closed in all failure paths without leakage.
- Framing & Protocol: Bounded framing prefixes payloads with a 4-byte big-endian length header. Maximum request payload is strictly capped at 64 KiB; maximum response payload is capped at 2 MiB. Malformed JSON and oversized headers fail closed.
- Structured Results: Results return explicit verdicts (`CLEAN`, `DETECTED`, `UNSCANNED`, `ERROR`, `BUSY`). Communication failures, truncations, and errors always exit with non-zero status (code 3) and are never treated as CLEAN.

3. WORKER ISOLATION & PROTECTION REUSE
- Snapshot Sealing: The received file descriptor is copied into an anonymous Linux `memfd` (`MFD_CLOEXEC | MFD_ALLOW_SEALING`) subject to running size limits (`--max-size`, default 50 MiB). The memfd is sealed with `F_SEAL_WRITE | F_SEAL_GROW | F_SEAL_SHRINK | F_SEAL_SEAL` before worker invocation.
- Process Confinement: The Phase 3B.1H supervised scanning path is executed on the sealed snapshot. The worker is spawned in a separate process group (`setpgid(0, 0)`), virtual address space limit is applied via `RLIMIT_AS`, environment is cleared (`env_clear()`), and Landlock ABI 1 deny-all filesystem isolation is activated before untrusted input parsing.
- Deadlines & Reaping: The coordinator supervisor enforces worker execution deadlines (`--worker-timeout-ms`, default 10s). On timeout or crash, `SIGKILL` is sent to the worker process group, and the direct child is reaped.

4. DATABASE TRUST & LOADING BEHAVIOR
- Trust Requirements: At startup, `raxosentinel serve` requires an explicitly selected, verified private generation (`--private-db-root` and `--private-generation`) or an authenticated signed-public release (`--public-release`, `--public-key`, `--public-approval-key`, `--public-state`). Legacy database options (`--db`, `--db-store`) are rejected.
- Startup Verification: The generation/release is verified before the coordinator binds the socket or accepts client connections.
- Loading Behavior: Workers spawned by the coordinator independently reload and re-verify the database generation files under Landlock rules. The database is NOT loaded into coordinator memory or shared across workers in this prototype.

5. EXACT COMMANDS
- Start Coordinator (Private Generation):
  target/release/raxosentinel serve --socket /tmp/raxo_runtime/raxosentinel.sock --private-db-root /path/to/db_root --private-generation fixture
- Start Coordinator (Signed Public Release):
  target/release/raxosentinel serve --socket /tmp/raxo_runtime/raxosentinel.sock --public-release /path/to/release --public-key /path/to/key.pub --public-approval-key /path/to/appr.pub --public-state /path/to/state
- Submit Scan via Dedicated Client:
  target/release/raxosentinel client --socket /tmp/raxo_runtime/raxosentinel.sock /path/to/target.txt --json
- Submit Scan via Standard CLI Wrapper:
  target/release/raxosentinel scan --socket /tmp/raxo_runtime/raxosentinel.sock /path/to/target.txt --json
- Preserved Direct CLI Scan:
  target/release/raxosentinel scan /path/to/target.txt --json --private-db-root /path/to/db_root --private-generation fixture
- Preserved Supervised CLI Scan:
  target/release/raxosentinel scan --supervised /path/to/target.txt --json --private-db-root /path/to/db_root --private-generation fixture

- Memory Model Note (User-space RSS vs Kernel memfd):
  Reported process RSS/HWM captures only mapped user-space pages. The sealed anonymous memfd snapshot is held in the Linux kernel shmem/tmpfs layer (`Shmem` in /proc/meminfo), consuming an additional ~file size of kernel RAM (e.g. 1 MB, 10 MB, 50 MB) during scan execution, which is reclaimed when the descriptor is closed.

8. OUTSTANDING LIMITATIONS & SECURITY BOUNDARIES
- Not complete sandboxing: Hostile code that intentionally detaches from its session/process group can outlive the supervisor group kill. Parent cannot generally reap grandchildren.
- Lack of cgroup v2 containment: In this container environment, `/sys/fs/cgroup` is not writable for uid 1000 and no delegated cgroup v2 subtree is available. No tree-wide `memory.max`, `pids.max`, or `cgroup.kill` is enforced.
- Concurrency scope: Single active scan runner with bounded pending queue. A multi-worker process pool is not implemented in this milestone.
- Identity separation: The coordinator and worker processes execute under the same user identity. Verified database files, keys, and state files must remain accessible to this identity during worker initialization.
- Future deployment requirements: Dedicated worker user identity, delegated cgroup v2 controller placement, openat2 path resolution restrictions, and full request-lifecycle timeouts.
